# ATLAS B2 — Test Plan V2 Design

Date: 2026-09-27
Status: DESIGN READY / NOT DEPLOYED
Branch: audit/b2-generalization-20260927

## Purpose
Preserve the certified B2 V1 installation/test history while allowing future company installations to certify the conversational behaviors discovered during FingerFood without hardcoding FingerFood-specific data into CORE.

## Compatibility rule
V1 remains immutable.
V2 is additive and coexistable.
No migration in this branch may rewrite historical test plans, test results, G03 approvals, certificates, or activation records.

## Current B2 V1 facts
B2 V1 uses 18 top-level installation tests.
The materializer and G03 readiness contain explicit cardinality assumptions around those 18 cases.
B2.2L.5 continuity also checks that 18 active definitions exist.

Therefore V2 must not be introduced by silently changing the V1 definition set.

## V2 strategy
Keep the top-level capability model stable initially and strengthen the assertion contract within existing capabilities.

Mapping:

### KNOWLEDGE_SEARCH_ACCURACY
Must include:
- CANONICAL_SOURCE_GROUNDING
- UNSUPPORTED_FACT_REJECTION
- UNSUPPORTED_ATTRIBUTE_INFERENCE_BLOCKED

### COMMERCIAL_RULES_ENFORCEMENT
Must include:
- AMBIGUITY_REQUIRES_CLARIFICATION
- ACTION_INTENT_GATING
- EXPLICIT_ACCEPTANCE_GATING
- MODIFICATION_OVERRIDES_STALE_ACCEPTANCE

### EXTERNAL_CONVERSATION_E2E
Must include:
- CONVERSATION_CONTEXT_CONTINUITY
- ACKNOWLEDGEMENT_NO_ACTION_RETRIGGER
- SELF_CORRECTION_FINAL_INTENT_WINS
- CONTEXTUAL_MODIFICATION_NO_LOOP

### DOCUMENT_TEMPLATE_OUTPUT
Must include:
- DOCUMENT_BOUND_TO_CURRENT_CANONICAL_STATE

## Company-specific data
The V2 assertions must operate against company canonical configuration generated by B2.
They must never contain hardcoded:
- product names;
- prices;
- city;
- bank/payment identifiers;
- phone numbers;
- brand-specific aliases;
- FingerFood-specific business rules.

## Visual grounding
B2 already includes MEDIA_TECHNICAL_DOCUMENTS as a conditional company requirement.
V2 should add a visual functional assertion only when the manifest/canonical data marks catalog media as applicable.

Proposed assertion:
VISUAL_REFERENCE_MATCHES_CANONICAL_ENTITY

This assertion should validate that:
- the requested entity/family is resolved from current message before stale memory;
- the returned media belongs to the canonical product/family;
- duplicate upstream assets are reported as asset-quality issues, not falsely classified as resolver failures;
- family-level media and variant-level media are distinguishable.

## Synthetic conversation generation
A future B2 V2 runner should generate company-specific synthetic conversations from canonical config instead of storing FingerFood phrases.

Scenario templates should include:
- direct request;
- ambiguous request;
- short acknowledgement;
- correction in same message;
- correction in next message;
- question after quote;
- modification after quote;
- unsupported product attribute;
- unsupported popularity/availability claim;
- media request;
- explicit acceptance;
- non-acceptance acknowledgement;
- post-modification acknowledgement;
- payment attempt before valid acceptance.

The template supplies structure.
The company canonical config supplies entities, products, values, policies and allowed actions.

## Versioning proposal
- assertion contract: B2_TEST_ASSERTIONS_V2
- plan contract: B2_INSTALLATION_TEST_PLAN_V2
- materialization contract: B2_TEST_PLAN_MATERIALIZATION_V2
- readiness contract: B2_TEST_READINESS_G03_V2

V1 RPCs stay callable for historical verification.
V2 RPCs are new names/functions.
Do not replace V1 functions in-place.

## Cutover gate
No future installation should use V2 by default until:
- V2 SQL passes static/smoke tests;
- a non-FingerFood synthetic company passes;
- FingerFood passes as regression;
- G03 V2 readiness is reproducible;
- certificate provenance records V2 contract/hash;
- rollback to V1 remains possible for historical installations.
